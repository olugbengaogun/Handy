## Fork-specific guidance

This is "Handy Plus" — a personal fork of `cjpais/Handy` (upstream, remote name `upstream`) that intentionally diverges (rebrand, extra features) but still wants to keep merging in upstream's improvements via a low-effort `git fetch upstream && git merge` workflow, including a daily automated sync (`.github/workflows/sync-upstream.yml`) that auto-merges when clean and only opens a PR when something collides.

**Before implementing any nontrivial change here, actively consider whether it increases future upstream-merge conflict risk** — e.g. broad rewrites of files CJ actively maintains, or restructuring shared code paths he's likely to also touch. If a change would make merges messier than necessary, **push back and propose the lower-conflict alternative** (additive settings fields/DB columns, wrapper functions, new isolated files/components) rather than silently implementing the riskier version. This is a standing instruction from the repo owner.

**Versioning:** as of this fork, `version` in `tauri.conf.json`/`Cargo.toml`/`package.json` is on its own line (`1.0.0+`), intentionally decoupled from upstream's `0.x` numbering so users can't confuse a Handy Plus build with vanilla Handy. Version bumps for this fork's own releases are done deliberately, not inherited automatically from an upstream merge — the daily sync may occasionally flag a real (but low-stakes) conflict on just that one line when CJ bumps his own version; when that happens, keep this fork's version, don't take upstream's.

**Before cutting a release, check what is actually published — never trust the local version number.** This fork's version is not chosen by hand alone: the daily upstream sync bumps it and cuts a `chore: release vX.Y.Z (automated upstream sync)` commit whenever CJ publishes his own release. So a working copy that has not been pulled recently reports a version that has _already shipped_, and a release cut from it either collides with an existing tag or hands users a build older than the one they are running. Always:

```bash
git fetch origin --tags
git tag --list 'v[0-9]*' | sed 's/^v//' | sort -V | tail -1   # what is really out there
git rev-list --left-right --count origin/main...HEAD          # left must be 0
```

then pick the next version above that. `release.yml` enforces this — it refuses to run when the version in `tauri.conf.json` is not strictly newer than the highest published tag — but the check exists to catch the mistake, not to excuse making it. Note also that the version being ahead of the last _local_ tag proves nothing; only the remote tag list counts.

**Release notes are product copy, not a changelog.** `src/content/release-notes/*.md` is bundled into the app — `releaseNotes.ts` globs it at build time — and shown in the What's New dialog on the first launch after an update, plus About → release history. Users read it. **Never generate it from commit subjects.** `fix(audio): move blocking cpal work off the main thread + lock-free is_recording` is accurate, useful to CJ, and meaningless to someone who just wanted dictation. The daily sync builds these notes from a fixed vocabulary table in `sync-upstream.yml`: commit subjects are only ever **matched** against that table, never echoed, which is what makes unreadable output structurally impossible rather than merely unlikely. A hand-written file for a version always beats the generated one — write one whenever a release deserves real prose. Anything asserted in these notes must be true of the shipped app; a claim like "Handy Plus updates itself" is wrong, because `UpdateChecker` only detects an update and prompts.

**This fork publishes exactly one target: `aarch64-apple-darwin`.** `release.yml`'s matrix has a single entry and every published asset is Apple Silicon — no Intel Mac, no Windows, no Linux. Upstream work touching only other platforms is invisible to every Handy Plus user, which is why the notes generator filters it out. If a second target is ever shipped, revisit that filter.

CI is trimmed to match, because a red X on a platform nobody can install is pure noise: `main-build.yml`'s matrix carries a single macOS entry where upstream has seven, and **`nix-check.yml` is disabled at the repo level, not in the file** — `gh workflow enable nix-check.yml` brings it back. Disabling it through the API rather than by editing its triggers keeps the file byte-identical to upstream's, so the daily sync never has to resolve a conflict there; the cost is that the file looks live when it is not, which is why it is recorded here. Both exist to keep failure mail about Linux and Windows out of the owner's inbox. Revisit if this fork ever ships a second target.

**The daily sync pushes with `SYNC_PAT`, not `GITHUB_TOKEN`.** GitHub refuses any push from the built-in token that touches `.github/workflows/`, with no permission flag that lifts it — so before this, any sync that merged an upstream CI change was discarded whole at the final push. Sync release commits also carry a skip-ci marker: PAT pushes (unlike `GITHUB_TOKEN` pushes) _do_ fire `on: push` workflows, so without it every sync would run main-build alongside the release build it already dispatches, building the same commit twice. Sync commits therefore show no CI runs of their own — expected, not broken.

Additional local-only working instructions (release-rerun policy, automated bug-sweep and plan-upgrade triggers, commit-authorship rule) live in `CLAUDE.local.md`, which is git-ignored and never pushed.

**English strings go in `plus.json`, never in `translation.json`.** AGENTS.md tells you to add new keys to `src/i18n/locales/en/translation.json`; in this fork that instruction is wrong and actively harmful. `translation.json` is upstream's file and is kept **byte-identical to cjpais/Handy** so that it merges fast-forward every single time. Everything this fork changes about the English copy — the 16 rebranded strings and the ~120 keys for features upstream does not have — lives in `src/i18n/locales/en/plus.json`, which `src/i18n/overlay.ts` merges on top at load time. Editing upstream's file in place is what made it the most conflict-prone path in the repository: CJ touches it in most commits, and a fork edit on the same line turns each of those into a conflict that stops the daily sync dead — on 2026-08-31 one reworded string blocked six upstream commits for five days. The other 23 locales have no overlay and are used exactly as upstream ships them.

The one thing an overlay can hide is upstream rewording a string this fork overrides, leaving the fork shipping stale English with no conflict to notice. `bun src/i18n/overlay.test.ts` and `bun run check:translations` both re-derive every override from the current upstream string and fail if one no longer matches; when that fires, re-derive the override from the new text rather than suppressing it. An overlay cannot express a _deletion_, so a key this fork wants gone stays in `translation.json` unused — delete the component, not the string.
